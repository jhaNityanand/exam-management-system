Backend roles, capabilities & policies

How the /admin workspace is gated: Application Admin vs Organization Admin, named capabilities, Laravel model policies, and exam-session ownership rules.

Laravel policies admin + org_admin content / organization / platform Updated August 2026

Overview

Panel access is limited to membership roles admin (Application Admin) and org_admin (Organization Admin). Candidates use /account only. Editor / Viewer panel roles remain deferred.

auth→admin→admin.capability:*→Policy / org scope
  • EnsureAdminAccess (admin) — must have an active panel membership.
  • EnsureAdminCapability (admin.capability:…) — named capability for sensitive route groups.
  • Model policies — content CRUD and attempt ownership, scoped to the current organization.
Canonical capability definitions live in App\Support\AdminCapabilities. Role strings live in App\Support\OrganizationRoles.

Roles

Role keyLabelEntryNotes
admin Application Admin /admin Full panel access (same as Organization Admin today).
org_admin Organization Admin /admin Full panel access (same as Application Admin today). Privilege split deferred.
candidate Candidate /account No admin panel. Own exams, attempts, profile, and results only.

Membership resolution prefers the highest-privilege active panel role (admin before org_admin) when a user has multiple organization rows.

Legacy Editor / Viewer strings are not panel roles today. Fine-grained RBAC for those roles is deferred (see TODO.md).

Capabilities (Aug 2026 matrix)

Capabilities are coarse gates used by middleware and helpers. Today both panel roles receive all capabilities. Constants and route groups remain so privileges can be narrowed later without rewriting controllers. Model policies still enforce org ownership.

Capability Covers admin org_admin
content Questions, exams, blogs, news, gallery, candidates (and related list APIs) Yes Yes
organization Org branding, members, FAQs, SEO settings, advertisements / placements Yes Yes
platform Cache & optimize, maintenance, email/SMTP, integrations, security Yes Yes
Future split: remove platform (or other capabilities) from AdminCapabilities::forRole(ORG_ADMIN) only — routes already use admin.capability:*.

Route groups

  • admin.capability:organization — advertisements + organization / SEO settings.
  • admin.capability:platform — cache, maintenance, email, integrations, security.
  • Content modules sit under auth + admin; policies require the content capability plus org match.

Model policies

Policies share AuthorizesOrganizationResources: panel membership, capability check, and organization_id match against the resolved current organization.

PolicyWho may actTypical rules
ExamPolicy Panel users with content viewAny/create; view/update/delete/restore/forceDelete/publish only for org-owned exams.
QuestionPolicy Panel users with content Same pattern for question bank records in the current org.
BlogPolicy / NewsPolicy Panel users with content CRUD + restore scoped to the organization.
GalleryPolicy Panel users with content Media CRUD, edit, restore, force-delete within the org.
AdvertisementPolicy Panel users with organization Ads / placements require organization capability (aligned with route middleware).
ExamAttemptPolicy Candidate owner or content admin view: attempt owner, or content admin for org-scoped review.
update / submit: attempt owner only.
Controllers should authorize via Form Requests or $this->authorize() so policies stay the single source of truth. Further bulk/JSON endpoint hardening remains on the backlog where not already covered.

Middleware stack

AliasClassBehaviour
auth Laravel session auth Must be signed in.
admin EnsureAdminAccess Active membership in admin or org_admin. Unauthorized users get a permission page (not a silent redirect).
admin.capability:{name} EnsureAdminCapability Requires content, organization, or platform for the user’s active panel role. 
// routes/web.php (simplified)
Route::middleware(['auth', 'admin'])->prefix('admin')->group(function () {
    // content modules…

    Route::middleware('admin.capability:organization')->group(function () {
        // advertisements, organization settings, SEO…
    });

    Route::middleware('admin.capability:platform')->group(function () {
        // cache, maintenance, email, integrations, security…
    });
});

Exam conduct security

Live attempts are owned by the candidate. Session tokens reduce multi-tab / multi-device cheating when single-session enforcement is enabled.

  • Ownership — ExamAttemptPolicy allows only the attempt’s user_id to update or submit. Admins with content capability may view org attempts for review.
  • Session token — ExamSessionService stores a per-attempt session_token. When proctoring policy enables single-session enforcement, live requests must send the token via X-Exam-Session-Token header or session_token input.
  • Mismatch — wrong or missing token returns HTTP 409 with a clear “open in another session” message.
  • Resume — starting again resumes the active attempt when the same session token is presented; a conflicting token is rejected.
  • No ads on runner — the live exam runner does not inject advertisement slots (focus and integrity).
  • Answer secrecy — candidate payloads omit correct answers; scoring runs server-side on submit.
Session tokens complement — they do not replace — authentication, CSRF, and ownership checks. Keep APP_DEBUG=false in production so stack traces and tokens are never exposed to clients.
